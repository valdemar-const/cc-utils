# Формат `.pipeline` — спецификация

Канонический справочник формата файла проекта cc-workbench. Термины, XML-структура, правила расширения и модели взаимодействия. Конвенция вендора узлов/плагинов — см. `plans/domains.md`; здесь — контракт самого файла и всего, что его окружает. Изменения формата обязаны обновлять этот документ в том же коммите.

**Текущая версия схемы: 2** (`cc::workbench::k_pipeline_format_version`, `projects/bin/cc-workbench/src/pipeline_xml.hpp`).

---

## 1. Термины

| Термин | Определение |
|---|---|
| **Документ** | Один `.pipeline`-файл: зафиксированный срез словаря + граф узлов + layout. |
| **Хост-среда** | Всё, что доступно workbench в текущей сессии: загруженные плагины, их домены/типы/фабрики + runtime-регистрации (Metadata-таб). |
| **Проектная среда** | Контракт документа: root-домен + imports. Единственный источник палитры узлов. |
| **Домен** | Открытая палитра-словарь (`domain_desc`: id, display_name, description, depends_on, provided_types). Seeder ≠ owner: любой плагин может дополнить любой домен. |
| **Root-домен** | Домен документа, выбирается при создании, иммутабелен весь срок жизни файла. |
| **Import** | Дополнительный домен, явно перечисленный в контракте. |
| **Замыкание** | `closure({root} ∪ imports)` — транзитивное расширение по `depends_on`. Определяет видимость фабрик: узел видим ⇔ хоть один его домен ∈ замыкания. |
| **Тип соединения** | Пин-тип (`value_type_desc`: name PascalCase, short_name, description). Регистрируется pipeline-плагинами; глобально уникален по имени. |
| **Inline-редактор** | Виджет ручного ввода значения пина. Регистрируется ХОСТОМ по имени типа соединения (`register_inline_editor`) — не плагинами. |
| **Узел** | Экземпляр типа узла на графе. Идентифицируется парой `type_id` + `instance_id`. |
| **Instance id** | Строка, уникальная в графе. Генерируется фабрикой (счётчик сеанса) либо восстанавливается из файла (`create_with_id`). При коллизии создания — регенерация (см. §6). |
| **Слот (пин)** | Типизированный вход/выход узла. Идентификаторы слотов — единый namespace на узел: input и output одного узла не могут зваться одинаково. |
| **Ребро** | `(src_node, src_slot) → (dst_node, dst_slot)`. Ссылается только на имена; имена типов не сериализуются. |
| **Inline-значение** | Текст значения неподключённого входного пина (`slot_values()`), парсится редактором типа и инъектируется runner'ом как обычный вход. Провод побеждает. |
| **Провайдер** | Плагин, зарегистрировавший фабрику узла (`<requires>`). Ортогонален доменам. |
| **Pipeline-плагин** | Dlopen-модуль, расширяющий словарь: домены, типы соединений, узлы (§7.1). |
| **Workbench-плагин** | Расширение редактора: inline-редакторы, view-рендереры, адресация типов по имени (§7.2). |
| **Тип-пакет** | Разделяемая библиотека — якорь typeinfo opaque-типа, линкуется на сборке (§7.3). |

## 2. Структура XML (v2)

```xml
<?xml version="1.0" encoding="UTF-8"?>
<pipeline version="2" domain="compiler/lang/tl">
  <!-- 1. imports: дополнительные домены контракта (0..n) -->
  <imports>
    <domain id="system/process"/>
  </imports>

  <!-- 2. requires: уникальные провайдеры всех типов узлов графа -->
  <requires>
    <plugin name="tl"/>
  </requires>

  <!-- 3. nodes -->
  <nodes>
    <node type="filesystem.path" id="filesystem.path#1">
      <pos x="-560" y="124"/>                      <!-- опционально, canvas-local -->
      <properties>                                  <!-- schema-driven, verbatim -->
        <property key="out_path">./out</property>
      </properties>
      <values>                                      <!-- inline pin values -->
        <value slot="in">./examples/42_answer.tl</value>
      </values>
    </node>
  </nodes>

  <!-- 4. edges -->
  <edges>
    <edge src_node="filesystem.path#1" src_slot="path"
          dst_node="filesystem.get_file#41" dst_slot="path"/>
  </edges>
</pipeline>
```

Правила:

- Атрибут `domain` **обязателен**; его отсутствие в v2 — ошибка загрузки.
- Порядок детей корня фиксирован: `imports`, `requires`, `nodes`, `edges` (`imports` опциональна и пишется только при непустом списке; остальные всегда присутствуют).
- Тексты `<property>` и `<value>` хранятся **дословно**: без резолва путей, канонизации, экранирования. Резолв относительных путей против каталога файла происходит при активации (`activate_context::pipeline_dir`), не в слое хранения. Это делает файл переезжаемым: round-trip сохраняет написанное пользователем.
- `<values>` — отдельное пространство имён от `<properties>` (ключ — slot id, не property key), другой потребитель (runner vs логика узла).
- Позиции — canvas-локальные пиксели imgui-node-editor; опциональны, при отсутствии узел располагается редактором.

## 3. Версионирование

| Версия | Семантика загрузчика |
|---|---|
| `1` | Legacy: `domain`-атрибута нет. Загружается с пустым контрактом, `legacy=true`, **все** фабрики видимы. Модалка предлагает миграцию: Save заставляет выбрать домен → файл перезаписывается как v2. |
| `2` | Текущая: контракт обязателен, семантика — этот документ. |
| `>2` | Отказ («this build understands up to 2»). Даунгрейда нет. |

Bump версии — при любом обратно-несовместимом изменении схемы; добавление опциональных элементов/атрибутов bump'а не требует.

## 4. Контракт доменов: правила

1. **Root иммутабелен** — не меняется после создания файла ни UI, ни загрузчиком.
2. **Добавление import свободное**: любой домен хост-реестра, кроме root и явных дубликатов. Транзитивно видимый dep можно закрепить явно — явное ребро переживает удаление dep из `depends_on` upstream-домена.
3. **Удаление import** (Metadata-таб): разрешено, пока после сжатия замыкания каждый поставленный узел остаётся видимым. Проверка по видимости (не по членству): мульти-доменный узел не блокирует, узел, тянувший словарь транзитивно через удаляемый, — блокирует; список блокеров показан в UI. Деструктивное удаление с orphan-узлами — future-work (`<orphans>`).
4. **Загрузка**: root-домен не зарегистрирован ни одним плагином → **hard error** (контракт документа нарушен). Import не зарегистрирован → warning, граф грузится.
5. **Сохранение** без root — ошибка («create it via the New Pipeline dialog»).

## 5. Две среды и палитра

- **Хост-среда** шире проектной всегда. Metadata-таб редактирует проектную среду (контракт) и расширяет хост-среду (runtime-домены — session-only, в файл не сериализуются).
- Палитра create-menu/drag-palette = фабрики, видимые в `closure({root} ∪ imports)`; пересчитывается каждый кадр — редактирование контракта мгновенно меняет палитру.
- Типовой цикл «освободиться от зависимости»: добавить домен (хост его видит) → наполнить узлами → сохранить → позже открыть, удалить узлы (список зависимых виден у каждого import) → удалить домен из контракта → сохранить.

## 6. Идентичность узлов

- `instance_id` уникален в графе; рёбра ссылаются на него.
- Фабрики генерируют id пер-процессными счётчиками, которые **не знают** об id, восстановленных из файла. Поэтому создание узла после загрузки идёт через регенерацию при коллизии (`spawn_node`): повторные `create()` до свободного id. Иначе — одинаковые editor pin-id, assert stacklayout.
- `slot id` — один namespace на узель: коллизия `in`/`out` делает разрешение рёбер двусмысленным (инцидент `filesystem.path`, вход переименован в `in`).

## 7. Архитектура расширений: три вида компонент

Платформу расширяют компоненты трёх принципиально разных видов. Смешение их ролей — типичная ошибка вендора; ниже — исчерпывающая таксономия.

### 7.1 Pipeline-плагин — расширение словаря

Расширяет **предметную область**: сеет домены, регистрирует типы соединений и узлы.

| Аспект | Значение |
|---|---|
| Артефакт | MODULE-библиотека `<runtime>/plugins/cc-plugin-<name>.so` (никогда не линкуется — только dlopen) |
| Точки входа | `extern "C" cc::plugin_info cc_plugin_load()` + `cc_plugin_register(host_registry&)` |
| Версионирование | `cc::plugin_api_version` (сейчас 4); хост отказывает в загрузке при несовпадении |
| Загрузка | Автообнаружение `plugin_loader'ом` на старте хоста; порядок произволен (регистрации merge'ятся, замыкание вычисляется при запросе) |
| Регистрирует | `register_domain` (сеет, не владеет), `register_value_type<T>` (внутри `push_domain`-scope), `register_node_factory` (фабрика заявляет `domains()`, мульти-членество допустимо) |
| Ничего не знает про | редакторы, view-рендереры, канвас, ImGui |
| Примеры | `cc-plugin-basic`, `cc-plugin-tl`, `cc-plugin-tl-ir`, `cc-plugin-x86_64` |

### 7.2 Workbench-плагин — расширение редактора

Расширяет **сам workbench** — то, как пользователь видит и вводит значения. К словарю отношения не имеет: адресует существующие типы соединений **по имени**, не по дескриптору.

| Аспект | Значение |
|---|---|
| Артефакт | Сегодня — in-process регистрация в хосте; целевое состояние — отдельные dlopen-модули со своим plugin-API (future work) |
| Регистрирует | inline-редакторы: `type_registry::register_inline_editor(type_name, control, parse)` — по имени типа, на ВСЕ пины этого типа у всех узлов; view-рендереры: `renderers().register_renderer` (по имени типа); перспективно — темы канваса, палитры цветов типов |
| Точка вызова | Дефолтный пакет хоста: `cc::runtime::register_inline_editors(host)` (`cc/inline_editors.hpp`) — String/Integer/Double/Boolean/Path/File; view-рендереры — `main.cpp` хоста |
| Ничего не знает про | реализацию узлов, activate(), структуру графа |
| Правило адресации | Только строковые имена типов (`"File"`), никогда `descriptor_of<T>` — у редактора нет права линковать тип-пакет чужого домена |

Принципиальное разделение: **pipeline-плагин отвечает на вопрос «какие слова есть в языке», workbench-плагин — «как их показывать и вводить»**. Поэтому редактор для `:file` регистрируется на стороне хоста и работает одинаково у любого вендора узлов — консистентность, а не удача.

### 7.3 Разделяемые библиотеки — тип-пакеты и логика

Обычные shared/static библиотеки, линкуемые **на этапе сборки** (не dlopen). Два подвида:

| Подвид | Назначение | Примеры |
|---|---|---|
| **Тип-пакет домена** | Cross-DSO якорь typeinfo opaque-типов: одна `.so` + заголовок `cc/types/<pkg>.hpp`; её линкуют ВСЕ плагины-производители и потребители типа — только тогда `aa::any_cast` сравнивает дескрипторы равными через границу DSO | `cc-types-filesystem` (`cc::fs::file_handle`) |
| **Библиотека логики** | Переиспользуемый C++-код внутри реализаций узлов; к ABI реестра отношения не имеет | `cc-parseit`, `cc-astq`, `cc-gen`, `cc-ir` |

Std-типы (String, Integer, Path) в тип-пакете не нуждаются — якорь libstdc++.

**Рецепт «объявить пин совместимым с типом чужого плагина»**: include заголовка тип-пакета + линковка → `descriptor_of<T>` идентичен у обоих DSO.Bridge-узел (знает словари двух доменов) при этом остаётся обычным pipeline-плагином с мульти-членством.

### 7.4 Матрица «кто кого видит»

| ↓ кто \ что → | Реестр (имена типов) | Тип-пакет (.so) | Редакторы | Реализация узлов |
|---|---|---|---|---|
| Pipeline-плагин | пишет (домены, типы, фабрики) | линкует | **не видит** | своя |
| Workbench-плагин | читает/пишет по именам | **не линкует** | регистрирует | **не видит** |
| Хост (workbench) | владеет | — | потребляет | через `activate()` |

Мост между 7.1 и 7.2 — только реестр имён; между 7.1 разных вендоров — только тип-пакеты; хост единственный, кто собирает всё вместе.

## 8. Отказоустойчивость загрузки

| Ситуация | Поведение |
|---|---|
| Файл отсутствует / битый XML / версия > текущей | hard error, модалка, граф пуст |
| Root-домен не зарегистрирован | hard error |
| Import не зарегистрирован | warning (`missing_domains`), граф грузится |
| Провайдер из `<requires>` не загружен | warning (`missing_plugins`) |
| `type` узла без фабрики | узел пропущен, warning (`unknown_node_types`) |
| Ребро на пропущенный узел | ребро пропущено, warning (`skipped_edges`) |

Мягкие предупреждения агрегируются в одну модалку после загрузки.

## 9. Headless-запуск и CLI (future work)

Целевая картина жизненного цикла документа:

```
$ cc-workbench /path/to/my.pipeline        # редактор открывает файл при старте
... edit and save

$ pipeline --run /path/to/my.pipeline -- arg1 arg2 arg3
$ echo $?
```

Семантика `--run` (проекция на существующие слои):

- **Headless-хост**: `make_host_registry` + `plugin_loader::load_all` + `load_pipeline` — тот же код, что в workbench; контракт доменов валидируется идентично (root отсутствует → hard error, import → warning).
- **Цель pull'а**: сегодня кнопка Run в workbench хардкодит `x86_64.assemble`. CLI требует явного **entry-point** — объявления в файле, какой узел/слот считать результатом.
- **Аргументы после `--`**: байндинг `argv` в граф. Кандидаты: выделенный source-узел args, чьи inline-слоты получает CLI, или декларативный маппинг в атрибутах корня.
- **Код возврата процесса** = Integer-результат entry-узла (иначе 1 + диагностика в stderr).

**Влияние на формат**: v2 не содержит entry-point и байндинга аргументов — это первый кандидат на v3 (опциональные атрибуты корня, старые файлы остаются валидными). Реализация — отдельный бинарь (условный `projects/bin/cc-run`) поверх cc-runtime + pipeline_xml; открытие файла по argv в самом cc-workbench — тривиально и не требует изменений формата.

**Дуальность потребителей (вопрос на подумать)**: один и тот же файл читают редактор и runtime. Вероятные категории узлов/атрибутов:

- **editor-only** — layout, view-отводы, палитрное состояние: при headless-запуске инертны или игнорируются;
- **runtime-source** — узлы, читающие окружение запуска как «аргументы скрипта»: argv, env, cwd, stdin (байндинг `-- arg1 arg2` из §9 — их inline-значения);
- **события / entry-points** — что триггерит вычисление (run-запрос; сегодня неявно — хардкод кнопки Run, в v3 — первый класс: узел или атрибут корня).

Разграничение — открытый дизайн-вопрос (флаг на фабрике? атрибут узла? отдельные type-семейства?); решения пока нет, зафиксирована только таксономия.
