# Домены предметной области — конвенция и механизм

Справочник вендора узлов/плагинов для cc-workbench. Реализовано в plugin API v4
(`cc/plugin_entry.hpp`), формат `.pipeline` v2.

## 0. Три уровня платформы

| Уровень | Что это | Кто определяет |
|---|---|---|
| **DSL** | визуальный граф: узлы, пины, рёбра — *словарь языка* | домены организуют словарь (видимость), пин-контракты — слова |
| **Реализация** | C++ внутри `activate()` — свободна: I/O, процессы, что угодно | вендор узла; домены не policing |
| **Документ** | `.pipeline` — зафиксированный срез словаря (root + imports) | пользователь при создании |

Домены живут только на DSL-уровне. Узел волен делать I/O внутри своей
реализации без всякой зависимости от `domain/filesystem` — домен это язык для
графа, не обязательный слой доступа к ресурсам.

## 1. Домен = открытая палитра

- Домен — «палитра контролов» (метафора Figma): `domain_desc {id,
  display_name, description, depends_on}` регистрируется через
  `host_registry::register_domain` (merge по id, идемпотентно).
- **Seeder ≠ owner.** Кто первый зарегистрировал — лишь сеет начальный
  словарь. Любой плагин может дополнить любой домен своими узлами и типами.
- **Членство самозаявляемое**: узловой плагин объявляет
  `node_factory::domains() -> span<const string_view>` (можно несколько —
  мульти-членство). Разрешение не нужно.
- **Мост-плагины** — рядовой случай мульти-членства: свой узел с
  `domains() = {d1, d2}` виден в палитрах обоих доменов.
- Переатрибуция *чужих существующих* узлов (shim-манифест) **не
  поддерживается**; вместо неё — свой узел-мост.
- Идентификаторы — dot/slash-path (`compiler/lang/tl`) — naming convention,
  **не иерархия**: вложенность не даёт видимости, только явные `depends_on`.

## 2. Видимость

- `visible = closure({root} ∪ imports)` — транзитивное замыкание `depends_on`.
- Узел видим ⇔ **хоть один** его домен ∈ замыкания.
- Циклы в `depends_on` безопасны (BFS с dedup), но считаются ошибкой дизайна.
- Пример карты (текущие плагины):

| Домен | Типы | Узлы | deps |
|---|---|---|---|
| `basic/types` | String/str, Integer/int, Double/double, Boolean/bool, Any/any | — | — |
| `filesystem` | Path/path, File/file, FileAttrs/attrs | path, get_file, get_or_create_file, file, read_text | basic/types |
| `basic/text` | — | text.constant | basic/types |
| `basic/view` | — | view | basic/types |
| `system/process` | — | exec | filesystem, basic/types |
| `compiler/lang/tl` | Ast/ast | tl.frontend, tl.irgen (мульти-вендор: tl + tl-ir) | basic/types, filesystem, basic/view |
| `compiler/backend/x86_64` | Module/ir | nasm_gen, assemble | basic/types |

## 3. Документ `.pipeline` (v2)

```xml
<pipeline version="2" domain="compiler/lang/tl">
  <imports><domain id="system/process"/></imports>
  <requires>...</requires>   <!-- плагины-провайдеры, без изменений -->
  <nodes>...</nodes>         <!-- + <values> для inline-значений пинов -->
  <edges>...</edges>
</pipeline>
```

- **Root-домен иммутабелен** после создания файла.
- **Imports**: добавление свободное — любой домен кроме root и явных
  дубликатов (транзитивно видимый dep можно закрепить явно: явное ребро
  переживает удаление dep из upstream-домена). Удаление в UI разрешено,
  пока безопасно: после удаления каждый уже поставленный узел графа должен
  оставаться видимым в сжатом замыкании (точная проверка — покрывает и
  узлы самого домена, и узлы, тянувшие словарь через его транзитивную
  цепочку). Деструктивное удаление с orphan-узлами — future-work
  (`<orphans>`-секция).
- Root-домен не зарегистрирован ни одним загруженным плагином → **hard error**
  (домен — контракт документа). Отсутствующий import → warning.
- v1-файлы грузятся в legacy-режиме (все фабрики видимы, `legacy=true`),
  Save предлагает выбрать домен (миграция в v2).

## 4. Типы значений

- `value_type_desc {name PascalCase, short_name, description,
  inline_control?, parse?}` — регистрируется в `type_registry`.
- Подпись пина на канвасе: `name:short` (дефолт имени пина = short-тип).
  Коллизия short-имён — не ошибка, тултип показывает full.
- Имена типов в XML не сериализуются — rename не требует миграции формата.
- **Inline-редакторы — расширение ХОСТА/workbench, не pipeline-плагинов**:
  `type_registry::register_inline_editor(type_name, control, parse)`
  регистрирует редактор по имени типа соединения, и каждый неподключенный
  вход этого типа — на любом узле любого вендора — ведёт себя одинаково.
  Pipeline-плагины объявляют чистый словарь (`value_type_desc` = имя +
  short + описание), без редакторов. Дефолтный пакет хоста —
  `cc::runtime::register_inline_editors` (String/Integer/Double/Boolean/
  Path/File); выделенный workbench-plugin API будет звать тот же entry point.
- **File-редактор**: текст резолвится против `pipeline_dir` и сразу
  stat-валидируется в `cc::fs::file_handle` (отсутствующий файл — ошибка
  валидатора у поля, ещё до запуска графа). Парсер получает `pipeline_dir`
  вторым аргументом.
- Текст хранится в `node::slot_values()`, инъектируется runner'ом как обычное
  входное значение; узлы-реализации не пишут fallback-код. Подключённый
  провод побеждает — редактор исчезает, ширина слота резервируется
  (Blender-DAG семантика default value).
- **Opaque-типы без редактора** (Ast, Module, FileAttrs) — только из узлов.

### 4b. Формы пинов — закрытое множество

Форма определяется осями `направление × подключённость × редактируемость`;
типы пинов и редакторы — открытые множества (плагины регистрируют),
форм — ровно шесть:

| Форма | Условие | Рендер |
|---|---|---|
| **F1 wired** | input + провод | `o name :short` — редактор скрыт, провод побеждает |
| **F2 editable-empty** | input + нет провода + есть редактор + пусто | `o name [:short]` — placeholder = подсказка типа |
| **F3 editable-filled** | input + нет провода + редактор + значение | `o name [text][...]` |
| **F4 opaque-required** | input + нет редактора + required | `o name :short` |
| **F5 opaque-optional** | input + нет редактора + optional | `o name :short` (dimmed) |
| **F6 output** | output | `:short name o` — никогда не редактируется |

Механика: хвост строки пина рендерится в одном из закрытого множества
**режимов отображения** (`draw_pin_value_field`): `editor` (живой
редактор), `ghost` (measure-only: те же вызовы виджетов внутри
вырожденного clip rect — `ItemSize` резервирует точную геометрию, но
`ItemAdd` отбрасывает всё как отсечённое: ноль пикселей, ноль интеракции;
используется при подключённом проводе), `annotation` (`:short`-метка для
типов без редактора). Множество редакторов открыто и ортогонально режимам:
какой из N редакторов активен — выбор слоя редакторов, режим определяет
лишь видимость. Узел пиксель-стабилен по ширине и высоте при
соединении/разъединении. Сам пин явным `ed::PinRect()` обрезается до
иконки; hover — свой ореол цветом типа в контенте узла (встроенные
PinRect-подсветки заглушены прозрачными `StyleColor_PinRect*` — pin-канал
рисуется поверх интерактивных виджетов); `BlueprintNodeBuilder::
DetachPin()` закрывает пин до виджета, так что выделение текста не
порождает линк. Новые виды редакторов (dropdown, slider, color) = новое
значение `property_kind` + одна ветка в `draw_pin_value_field` + парсер в
пакете редакторов.

### 4c. Константы Blender-style

Единственный носитель константы let-узла — inline-значение его входного пина
(`filesystem.path`: `in` необязательный, пусто → failure с понятным
сообщением). Отдельной property-fallback механики нет. multiline-источники
кода остаются property в футере (`basic.text.constant`).

## 5. Path ≠ File; handle + инспектор

- **Path** — синтаксис: инварианты именования, ноль метаданных, ноль I/O.
- **File** — материализация: канонический путь + снапшот метаданных
  (size/permissions/modified) на момент открытия/создания.
  «`Optional<File>`» живёт в диагностике: несуществующий файл = failure на
  activate (get_file — строгий; get_or_create_file — lenient для write-таргетов).
- **Инспектор-узел** (`filesystem.file`): пропускает handle насквозь +
  projection-выход `attrs` из снапшота. Без I/O при активации; свежий stat —
  будущий отдельный узел.
- Принцип «handle + инспектор» масштабируется (Process → ret_code/cout/cerr —
  уже так).

## 6. Паттерны источников значений

1. **«Значения только из явных узлов»** — базовый принцип DAG-чистоты:
   константа живёт в теле source-узла.
2. **Let-узел** (`filesystem.path`): опциональный вход + property-fallback +
   выход для fan-out. Коалесценция «пин или свойство» легальна как
   объявленный контракт конкретного узла.
3. **Inline-значение пина** — локальная ленивость (быстро задать параметр);
   let-узел — графовая именованность (переиспользование). Оба паттерна
   канонические; «когда что» — inline для одиночных параметров, let для
   разделяемых.
4. Слот-иды — один namespace на узел: вход и выход let-узла не должны
   зваться одинаково (`in` → `path`), иначе разрешение рёбер двусмысленно.

## 7. Тип-пакеты доменов (cross-DSO контракт)

Чтобы `any_cast` работал через границу DSO, typeinfo якорится в **одной**
shared-библиотеке, которую линкуют все потребители типа:

- `cc/types/filesystem.hpp` + `libcc-types-filesystem.so` — File/FileAttrs.
  Схема для вендоров: домен со своими opaque-типами ships тип-пакет
  (`cc_add_library`, PUBLIC_DEPS cc-core).
- std-типы (String, Integer, Path) в пакете не нуждаются (libstdc++).
- «Объявить пин совместимым с типом чужого плагина» = include заголовка
  тип-пакета + линковка: `descriptor_of<T>` идентичен у обоих.

Разбиение плагина на части: (1) тип-пакет домена, (2) библиотеки логики
узлов, (3) тонкий plugin-module с `cc_plugin_register`. Отдельная .so между
(2) и (3) не нужна — узлы зовут друг друга только через провода.

## 8. Формат метаданных и версионирование

- `<pipeline version="2">` — версия схемы формата; лоадер понимает ≤ своей
  мажорной, старшую отказывает.
- `plugin_api_version = 4` — версия контракта cc-core (домены,
  value_type_desc, slot_values).
- Порядок загрузки плагинов нерелевантен: регистрация доменов merge'ится,
  замыкание вычисляется в момент запроса палитры.

## Future work

- `<orphans>`-секция для удаления домена с сохранением сериализованных узлов.
- Workbench-plugin API (dlopen) для сторонних inline-редакторов и тем канваса
  — регистрация через тот же `register_inline_editor`.
- Новые inline-редакторы: dropdown (enum-опции), slider, color — расширение
  `property_kind` + одна ветка рендера + парсер.
- Пер-пиновые валидаторы inline-значений (только положительные int и т.п.).
- Third-party compat-shim'ы (заявление совместимости чужого узла).
- Integer/Double/Boolean-let узлы по рецепту `filesystem.path`.
- Свежий `stat`-узел для File.
- Алгоритмическая генерация цветов типов (заменит `pin_color_for_type`).
