# Как это должно работать

Есть платформа workbench. Пользователь открывать исполняемый файл и видит пустое imapp окно
без открытых табов и с главным меню, где он выбирает:

    'File' -> 'New...' -> 'Pipeline'

После чего открывается таб файла `unnamed.pipeline`, который является xml или toml форматов
и содержит граф узлов. Сам редактор - это пустой node canvas, который предстоит отредактировать.

Регистрация типов узлов для workbench происходит через единый плагинный механизм.
Волшебных встроенных узлов не существует, 0 плагинов, значит 0 узлов, значит программа ничего не умеет.

Но некоторые базовые плагины все же есть, например узел извлекающей текст из файла.
Или выходной узел задающей имя выходного исполняемого файла (принимает байты, сохраняет в указанный файл).

Помимо меню workbench содержит тулбар (под строкой меню) куда выводяться контекстные действия над текущим выбранным узлом.
Например выходной узел исполняемого файла возможно 'Compile', тогда он рекурсивно вычисляет узлы подключенные через входные пины транзитивно (фактически стартует compiler pipeline выстроенный в узлах).

Получается существует цепочка узлов между источником исходного кода и выходным бинарным блобом.

Пины узлов типизированы, есть абстракция над любым типом пина, каждый плагин регистрирует свои типы.
Существует общий generic механизм проверки соединений на соответствие типов.

Workbench должен иметь симпатичное контекстное меню канваса для удобного создания узлов из сгруппированных по смыслу подменю (PIE меню или классический вид popup меню).

В общем виде api плагинов должен позволять регистрировать свой узел, объявлять входные и выходные типизированные слоты, может предоставлять колбек рендеринга этого узла на графе для workbench, предоставлять функцию активации узла который из данных входных слотов сформирует данные выходных. Вызовом этих функций управляет workbench pipeline runner.
Также должна быть возможность зарегистрировать действия тулбара если данный узел выбран активным.

Цвета типов регистрируемых плагинами workbench может алгоритмически генерировать обеспечивая контрастный вид и уникальность. Не обязательно закреплять на момент регистрации плагина.
Таким образом отображение графа должно быть консистентно а его логика отображения обособлено. Плагины регистрируют метаданные упрощяющие их отрисовку (семантику), но не определяющие внешний вид.

Что бы упростить отладку конвейера помимо редактора pipeline нужны табы просмотра выходных значений узлов или даже редакторы текстовых буферов (кода).
Например:

```
ImApp Window:
  Menu:
    Menu 'File':
      Menu 'New...':
        MenuItem 'Pipeline'
  ActionBar:
    <delegate:GetActionBySelectedNodeProvider>
  Layout:
    hbox:
      tab:
        editor:source   'unknown.pipeline'
      tab:
        editor:pipeline 'unknown.pipeline'
      tab:
        logger:output
  statusbar:
    vbox:
      spacer
      version_info
```

pipeline редактор - первичен. Для отладки есть возможность замкнуть выходной пин узла (дополнительным соединением) на специальный узел view (который принимает любой тип на вход), которому можно назначить имя через настройку. Затем открыв специальный 'File' -> 'New...' -> 'View', откроется View панель, где в выпадающем списке на самом верху можно выбрать по имени какие данные отображать. То есть если на node graph есть узел 'View' с именем 'some code' и к которому подключен выход узла 'Source' типа 'Text' то таб View будет отображать этот текст.
